# 预测器补测：满队列的无效定时重试

首轮使用既有 `dispatch_fix/runtime.py`，在异构的历史/随机时长估计器上出现大量无效定时事件。
2026-10-08T11:40:29Z 启动的36点运行于612.80秒后主动终止；实际执行回执保留返回码1，不能作为完成结果。
首轮代码另存 `attempt1_run.py`、`attempt1_nominal_control.py`；已经完成的首轮nominal六点保留在
`nominal_control_attempt1/`。本轮完整结果来自后续 bounded 两份成功执行回执。

一个独立复现从18个开发窗口开始，按冻结顺序回放 `random`，在
`heldout_swe_b16_l2_s11` 的十秒诊断超时中捕获：

| 观测 | 值 |
|---|---|
| 当前模型时刻 | 3,074,925.195120118 ns |
| 核0队列 | `[0, 26]`，Current＋Next已满 |
| `capacity_to_bind` | False |
| pending事件数 | 7,025 |
| 正在执行 | 两核均有run actor，并非数据计算完成 |
| 热点 | `try_bind`仍调用`event(..., "bindcheck", ...)` |

队列满时，预测ETA到点不会释放Current、Next或任何物理存储。既有代码仍反复生成ETA计时检查，
不同核的检查又会生成彼此的后续检查，导致模拟器事件队列堆积。该诊断不是有效延迟结果，
也不应把程序运行墙钟时间混入模拟周期数。

本实验采用 `bounded_runtime.py` 的私有执行命名空间，仅改变一个条件：

```python
# 原条件
if outstanding and earliest-at > params.binding_lead_cycles+1e-7:
# 本次共同条件
if can_bind and outstanding and earliest-at > params.binding_lead_cycles+1e-7:
```

物理资源不足时不设置仅靠ETA的唤醒；仍由真实完成、阶段切换和既有进度事件重新检查。
有物理空间但尚未进入提前绑定窗口的核，保留原ETA计时器。参数、代价、队列容量、HBM、
任务和存储配额没有改变；原runtime文件及第二轮冻结结果没有修改。所有组织、估计器及nominal控制
共同采用此条件，不能把这项事件修复当作学习预测器或异构架构的收益。

后续完成36个主点和6个nominal控制点，每点18开发＋135留出窗口，两次完整新状态重复。
共12,852次窗口仿真，逐窗口保存5,670条结果和176,988条任务预测记录。
每点warmup、完整heldout结果和最终估计器状态均重复一致。

810条旧WS控制记录全部HBM字节相等，最大模型时间差为1.4528632164001465e-7 ns，
属于浮点舍入差。完整结果digest仅272条相同：冗余检查/日志删减改变了返回内容，
不能声称全部结果逐位相同。随机估计器的无效估计调用次数改变后，其随机数消耗也改变，
不与被终止的首轮随机轨迹声称逐位复现。

`test_bounded_runtime.py` 的三项回归全部通过：单核两模式三个batch完整结果逐位不变；
上述随机历史样例完成且pending高水位小于128；原dispatcher源码和函数保持不变。
