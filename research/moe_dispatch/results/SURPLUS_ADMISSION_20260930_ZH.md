# 剩余准入控制器：实现、实验与限制

**结论：提案已实现为独立开关，但“四条规则全开就能接近字节下界、使双核不再吃亏”的预期没有成立。** 256 信用确实限制小 batch 的可达带宽；晚绑定在 B8 异构上有局部收益；四级仲裁和长期占槽的跨阶段预取反而可能恶化结果。不能把这版机制直接写成已验证的普遍加速方案。

本次完成三组单变量实验192点、同预算累计消融132点、信用扫描36点，以及1024信用下的累计消融132点，共 **492点×2＝984次**，完整重复输出一致。另检查真实路由离线重组的 B32/64/128/256：12 个组织/批量点均被容量检查拒绝，没有虚构其运行时间。E3 依赖 E2 找到可行区间，本次未触发。

所有性能数字均是 Rust **解析时序模型结果**，不是 native Ramulator、RTL/芯片测量或完整模型推理。正式工作负载是归档 BFCL 的最后 token prefill 路由，B2/B4/B8/B16 为嵌套窗口；不能改称重新实测的 decode。路由和输入已驻留，计时到所有专家输出和路由顺序合并完成。大规模计时只处理地址/依赖/时序；实际数据正确性由小尺寸、真实事件轨迹驱动的 BF16/FP32 重放验证。

## E0：信用上限确实存在，但不能解释所有 batch

256×32 B／64 ns＝128 B/ns 是信用约束推导上限；实际接受到落地平均约65 ns，因此实测更低。B2 原配置约124–125 GB/s，已经接近这个上限。

512、1024 信用仅作为**明确超预算的因果诊断**：分别额外需要8／24 KiB返回容量，以及512／1536 B标签状态。它们不进入正式同预算胜负判断。因为提案同时要求“不加 SRAM”，本次没有把正式实验自动改成1024信用。

## 已测到的原因和还不能下的结论

- **晚绑定不等于增加选择。** B8异构的两个合法候选核绑定次数从3次降为1次，其余9次只有一个候选核。+2 的1.923379 ms确实比同条件单核2.038279 ms、同构2.171061 ms更低，但不能宣称这是更准确的双核预测决策带来的普遍收益。逐次预测误差与合法核数均已导出。
- **仲裁会改变最后任务的归属。** B8异构，+2时Shared在大核，+3时变成小核，另一个Me8专家转去大核；两核最后完成从1.9160/1.8804 ms变为1.6456/2.4858 ms，长尾显著扩大。这是实际归属记录，不应只解释成HBM不足。
- **跨阶段预取存在污染。** B8异构，+3与+4专家归属相同。+4下一阶段tile占槽时间约占两核观测窗口25.7%/36.1%；权重未就绪观察从425,460/441,346周期升到555,050/559,635周期。B16的归属也相同，+4耗时更长。提前取少量下一阶段数据，却长期减少Current可用深度，是与这些观察一致的解释；不是对所有差值的可加墙钟分解。
- **E不是计算就绪证明。** 在途字节可能尚未到齐，已落地数据可能还受X、K依赖或端口限制。因此E阈值只能作为供数估计。严格优先级只约束新请求选择，已接受的低优先级请求仍占信用和端口，不能保证零干扰。
- **Me≈96不是当前硬件的实测分界。** 该值来自12,288 MAC/周期吃满的理想算术峰值，而当前满宽X读取约16周期，满占用持续供数上限约768 MAC/ns，还没计其他依赖。因此不能先验地把B2–B16都判为HBM受限。

## 实现修正与资源账

Compiler生成每核8档Me深度/门限表；Runtime在任务提升时收费读取。D至少覆盖G=4驻留带，超过物理槽时明确截断。`可借槽=max(0,free−max(min(D,当前阶段剩余tile)−Current持有,0))`，避免负数和保护不存在的尾部tile。E在请求接受时计入，落地不再增加，最后一次实际读结束才回收。已锁定的valid请求在背压下不改变归属。

新增政策寄存器32 B，剩余准入查表/缓存门限/跨阶段游标等保守预留160 B；全部在原4 KiB控制预算内。总控制状态单核2,944 B、双核3,936 B，余量1,152 B／160 B。没有综合结果，也不声称逻辑在1GHz单周期可实现。

## E2：为什么大 batch 没有延迟数据

使用`real_shared_moe_routes_20260819`中的512请求档案，取layer1、decode step0的不同真实请求，离线重组成B32/64/128/256。保留专家ID和得分，附源文件hash。这是路由重组场景，不是新采集的大batch完整推理。

当前把原输入、每专家输出inbox、最终输出等一直保留。**B32单核仅固定预留就有2,237,504 B，已经超过2,097,152 B总预算；算Shared时峰值达到2,999,360 B。** 双核各私有分区同样装不下。因此12点均在编译规划阶段拒绝，未启动无效计时。详见`E2_capacity/capacity.csv`和`expert_loads.csv`。不能把这些容量失败当成“Me≥128时多核没有性能收益”。

要继续E2，应先明确输出逐步合并/退役或M维分块的契约，并计入必要的额外流量。把B256简单拆成多个B16只能测小M分块吞吐，不能用来验证Me≥128的形状优势。

## 交付和判定

- `metrics.csv`、`binding_predictions.csv`：132点与逐次绑定预测/实际完成。
- `slot_occupancy.csv`、`arbiter_tiers.csv`：各核槽位分布、低存量风险事件和级3授权。
- `supply_idle.csv`：每核没有DMA接受的观察及另一核阶段/等待原因；不等于全局HBM空转。
- `campaigns/surplus__0b0b9234b4c2734d/core_front_states.csv`：独占前端观察，不能与其他核或算术周期相加。
- `E0_credit_diagnostic`：36点×2信用扫描（256为参考，512/1024明确超预算）；`E1_credit_diagnostic`：132点×2在1024信用下的累计消融；`E2_capacity`：真实路由和容量拒绝证据。
- 原来的三组单变量结果独立归档在`../moe_runtime_policy_ablation_20260930`。

按正式256信用、margin64的规则全开结果，三种组织没有被推到256 B/ns字节下界的个位数百分比以内，双核也没有全面不慢于单核。**本版不通过提案的系统收益预期；规则3/4保持实验开关，不默认推广。** 先解决信用/存储预算的一致性及Current深度估计，保留+2的局部收益作证据；不继续叠加RoofPair来掩盖当前问题。

测试记录：22个Rust、13个Compiler、31个Python测试通过，涵盖背压、尾部tile、跨阶段在途继承与实际事件驱动数值重放。测试日志在`reproduction/`。492个大尺寸计时点均检查工作量/字节守恒、容量、排空及重复一致；它们不执行模型数值。每个campaign的provenance固定了当时实际使用的源码和二进制，最终整理提交不替代这些运行证据。
